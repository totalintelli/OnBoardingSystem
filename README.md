# OnBoardingSystem

기업 내 신규 직원의 온보딩 시스템(회사 내규, 업무 규정 등)

신입 직원이 사내 규정을 질문하면 관련 규정 문서를 검색해 근거 기반으로 답변하고 출처를 표시하는 RAG(검색 증강 생성) 챗봇 프로토타입이다. 채용 과제용 프로토타입으로, 완성된 상용 서비스가 아니라 핵심 기능과 설계 판단을 보여주는 데 목적이 있다. 자세한 설계 배경은 [설계 스펙](docs/superpowers/specs/2026-08-31-onboarding-rag-chatbot-design.md), 구현 순서는 [구현 계획](docs/superpowers/plans/2026-08-31-onboarding-rag-chatbot.md) 문서를 참고한다.

## On-premise 전제

연차 일수, 경비 한도 등 사내 규정에 포함된 조직 내부 수치가 외부 LLM 제공사 서버로 전송되는 경로를 차단하기 위해, 임베딩·생성 모델을 외부 API로 호출하지 않고 전부 로컬에서 실행한다. 별도 API 토큰 없이 HuggingFace 오픈소스 모델을 로컬에 내려받아 구동한다.

## 아키텍처

```
data/docs/*.md (더미 규정 문서)
        │
        ▼
   rag.py (문서 청크 분할 → 임베딩 → 코사인 유사도 검색)
        │  top-k chunk + 유사도 점수
        ▼
   llm.py (로컬 소형 LLM, 검색 결과를 컨텍스트로 답변 생성)
        │  답변 + 참조 문서 목록
        ▼
   app.py (Streamlit 채팅 UI, 답변 아래 출처 표시)
```

설계에서 의도적으로 선택한 지점은 다음과 같다.

**벡터 DB를 쓰지 않았다.** 전체 청크가 수십 개 수준이라 numpy 배열 전수 비교로 충분하고, FAISS 같은 의존성을 추가하면 얻는 것 없이 설치·운영 복잡도만 늘어난다. 문서 규모가 수천 건대로 커지면 그때 도입할 문제다.

**검색 결과를 2개로 제한한다.** 조각을 많이 넘길수록 근거가 풍부해질 것 같지만, 실측에서는 반대였다 — 1.5B 모델이 서로 다른 조건의 숫자를 뒤섞어 문서에 없는 답을 만들어냈다. 컨텍스트를 좁히는 것이 이 모델 규모에서는 정확도에 유리했다.

**출처는 유사도 1순위 문서만 표시한다.** 프롬프트가 "가장 관련된 조각 하나만 골라 답하라"고 지시하므로, 검색된 모든 문서를 나열하면 실제 근거와 표시가 어긋난다.

## 진행 상태

- [x] 더미 사내 규정 문서 6종 (`data/docs/`)
- [x] RAG 검색 모듈 (`rag.py`) — 문서 청크 임베딩, 코사인 유사도 검색
- [x] 로컬 LLM 답변 생성 모듈 (`llm.py`) — 유사도 임계값 미달 시 fallback
- [x] Streamlit 채팅 UI (`app.py`) — 답변과 참조 문서 출처 표시

## 실행 방법

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

```bash
streamlit run app.py
```

브라우저에서 `http://localhost:8501`이 열린다. 최초 실행 시 임베딩·생성 모델을 로컬에 내려받으므로 몇 분이 소요될 수 있으며, 이후로는 캐시된 모델을 사용한다.

파이프라인(검색 → 답변 생성)이 정상 동작하는지만 빠르게 확인하려면:

```bash
python pipeline_check.py
```

## 데모 질문

아래 질문들은 검색이 의도한 문서를 1순위로 찾는 것을 실제로 확인한 것이다. 괄호 안은 검색된 문서와 유사도 점수다.

| 질문 | 검색 결과 |
|---|---|
| 연차는 며칠 쓸 수 있어? | `01_연차휴가.md` (0.726) |
| 경비는 얼마까지 쓸 수 있어? | `03_경비처리.md` (0.638) |
| 재택근무는 며칠 가능해? | `04_재택근무.md` (0.737) |
| 출근 시간이 어떻게 돼? | `02_근태.md` (0.779) |
| 비밀번호는 얼마나 자주 바꿔야 해? | `05_보안수칙.md` (0.856) |
| 건강검진 지원되나요? | `06_복리후생.md` (0.595) |

**질문은 문장형으로 하는 것이 좋다.** 같은 주제라도 `경비 사용 규정` 같은 명사구로 물으면 최고 유사도가 0.507까지 떨어지며 엉뚱한 문서가 검색됐지만, `경비는 얼마까지 쓸 수 있어?`로 바꾸면 0.638로 올라가며 정확한 문서를 찾았다. 사용 중인 임베딩 모델이 문장 단위 유사도에 최적화돼 있기 때문이며, 실제 챗봇 사용자는 대개 문장으로 질문하므로 이 특성이 실사용에 불리하지는 않다.

## 사용 모델

- 임베딩: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
- 생성: `Qwen/Qwen2.5-1.5B-Instruct`

두 모델 모두 CPU에서 동작하며 API 토큰이 필요 없다.

## 알려진 한계와 대응

프로토타입 범위에서 실측으로 확인한 제약과, 각각에 대해 어떻게 판단했는지를 적는다.

**임계값 기반 fallback은 튜닝이 남아 있다.** 유사도가 임계값(0.35) 미만이면 LLM을 호출하지 않고 "인사팀에 문의하세요"로 응답하는 경로를 구현했고, 이 분기 자체는 유닛 테스트로 검증했다. 다만 사용 중인 다국어 임베딩 모델은 의미상 무관한 문장 쌍에도 유사도 0.9 안팎을 반환한다 — 규정 문서에 대해 "오늘 저녁 메뉴 추천해줘"를 질의했을 때 0.90이 나왔다. 즉 이 모델에서는 **절대 임계값이라는 접근 자체가 성립하지 않으며**, 값을 0.35에서 올리는 것으로는 해결되지 않는다. 실무에서는 관련 질문군과 무관 질문군의 점수 분포를 측정해 상대적 판별 기준을 세우거나, 변별력이 높은 임베딩 모델로 교체하는 것이 올바른 접근이다.

**모델 규모는 환경 제약 안에서 선택했고, 그 한계가 답변 끝부분에 남아 있다.** 검색된 문서 조각의 내용 자체는 정확히 전달하지만, 모델이 답변 마지막에 "따라서 ~"로 요약을 덧붙이면서 문서에 없는 숫자를 합산하는 경향이 있다. 예를 들어 연차 질문에서 문서의 11일·15일·25일은 정확히 옮기면서도 마지막 문장에서 "총 16~30일"이라는 없는 값을 만들어낸다. 프롬프트로 이 습관을 억제하는 시도를 세 차례 했으나(계산 금지 명시, 요약 금지 명시, 긍정형 지시로 전환) 모두 실패했고, 특히 금지어를 프롬프트에 노출하자 오히려 그 표현으로 답변을 시작하는 역효과가 관찰됐다. 3B 모델로 교체를 시도했으나 실행 환경(가용 메모리 약 15GB)에서 float32 가중치 약 12GB를 올리는 과정에 메모리 스래싱이 발생해 되돌렸다. **이 문제는 프롬프트 엔지니어링의 영역을 넘어선 모델 용량 문제로 판단하며, GPU 환경에서 더 큰 모델을 쓰는 것이 올바른 해법이다.** 답변 본문의 사실관계는 문서와 일치하므로 출처 문서를 함께 확인하면 검증 가능하다.

**검색 품질이 문서 작성 방식과 질문 형태에 민감하다.** 섹션 제목이 질문의 표현과 어휘상 겹치지 않으면 엉뚱한 섹션이 검색됐다 — 초기 문서에서는 "연차는 며칠 쓸 수 있어?"라는 질문에 발생 기준이 아니라 신청 절차 섹션이 걸렸다. 여섯 문서의 섹션 제목을 질문형으로 바꿔 대응했고, 그 결과 대표 질문 여섯 개가 모두 의도한 문서를 1순위로 찾는 것을 확인했다. 다만 이는 문서 작성자에게 부담을 넘기는 방식이라 근본 해법은 아니며, 질의 확장(query expansion)이나 한국어 검색에 특화된 임베딩 모델이 다음 단계다.

**빈 청크가 근거 없는 답변을 유발했던 문제는 수정했다.** 초기 구현은 문서를 `##` 헤더 기준으로 분할하면서 `# 문서 제목`만 담긴 본문 없는 청크를 만들었다. 이 청크가 검색되면 모델이 내용 없는 제목만 받고서 "정보가 없다"고 답한 뒤 일반 상식으로 답을 지어냈고, 화면에는 출처까지 함께 표시돼 근거 없는 답변이 근거 있는 것처럼 보였다. 현재는 본문 없는 청크를 생성 단계에서 제외한다.
